# Acceptance Criteria: User Directory and Runtime Identity Redesign

**Spec:** `docs/superpowers/specs/2026-04-26-user-directory-runtime-identity-redesign.md`
**Date:** 2026-04-26
**Status:** Draft

---

## Criteria

| ID | Description | Test Type | Preconditions | Expected Result |
|----|-------------|-----------|---------------|-----------------|
| AC-001 | The control-plane schema defines `users`, `roles`, `user_roles`, and `org_nodes` tables, and `api_keys` includes nullable `user_id`. | Logic | Fresh database created from the new baseline migration. | Inspecting the migrated schema shows all four new tables, the `api_keys.user_id` column, and no missing referenced foreign keys. |
| AC-002 | The new baseline migration can initialize an empty database without requiring historical Alembic revisions. | API | Repository checked out with the redesign migration set only. | Running the migration command against an empty database succeeds and produces the expected latest revision with no dependency on prior migration lineage. |
| AC-003 | Runtime API keys must be bound to exactly one user. | API | A user exists and one active runtime key is already bound to that user. | Attempting to create or activate a second runtime key for the same user is rejected with a deterministic validation error. |
| AC-004 | Creating a user from the admin API automatically creates exactly one runtime API key and returns the plaintext key once. | API | Admin-authenticated request, at least one organization node exists, and any referenced roles exist. | The create-user response includes a new user record, one runtime key bound to that user, and one plaintext key value that is not returned by subsequent fetch requests. |
| AC-005 | Resetting a user key invalidates the previous runtime key immediately and issues a new plaintext key once. | API | An active user with one active runtime key exists. | After reset, requests authenticated with the old key are rejected, requests with the new key are accepted, and subsequent user fetches do not expose the plaintext key. |
| AC-006 | Disabling a user also disables that user's active runtime access. | API | An active user with one active runtime key exists. | After the user is disabled, runtime requests using that key return an authorization failure and the user detail shows disabled status. |
| AC-007 | Runtime MCP tools and direct HTTP tool endpoints reject request-supplied `user_id`, `roles`, and `groups` fields. | API | A valid runtime key bound to an active user exists. | Sending those identity fields to runtime endpoints results in request rejection or field-level validation failure; the request is not processed using caller-supplied identity. |
| AC-008 | Runtime authorization derives identity only from the authenticated API key binding. | Logic | A bound runtime key, user record, and assigned roles exist. | Internal runtime identity assembly resolves the correct `user_id`, assigned role ids, and `org_node_id` without reading identity values from the request payload. |
| AC-009 | Runtime requests authenticated by a user-bound key evaluate policies against `all`, `user`, and `role` subjects only. | Logic | Active user-bound runtime key, resource policy fixtures for `all`, `user`, and `role`. | Policy evaluation returns deterministic allow/deny decisions based only on the bound user and roles; no organization or group subject is consulted. |
| AC-010 | Governance policy forms and APIs no longer support `group` as a subject type. | API | Admin-authenticated request to create or update resource, field, or masking policy. | Any request using `group` subject type is rejected, and successful policy creation is limited to `all`, `user`, or `role`. |
| AC-011 | Runtime audit events include `api_key_id`, `user_id`, resolved roles, and `org_node_id`. | API | A bound runtime key executes at least one successful runtime tool call. | The resulting audit record contains the authenticated key id, the bound user id, the resolved role set, and the user's organization node id. |
| AC-012 | The admin console navigation includes `Users` and `Roles`, and there is no standalone organization page. | UI interaction | Admin is logged in to the web console. | The sidebar displays `Users` and `Roles`, and no separate organization navigation item is present. |
| AC-013 | The users page displays a left organization tree and a right user-management workspace in the same screen. | UI interaction | Admin is logged in and at least one organization node exists. | The page renders an organization tree pane, a user list pane, and user actions without navigating to a separate organization page. |
| AC-014 | Organization maintenance actions are available from the users page tree area. | UI interaction | Admin is on the users page. | The organization tree area exposes create root node, create child node, edit node, and delete empty node actions. |
| AC-015 | Creating a user in the console requires selecting organization and roles and then reveals the generated key once. | UI interaction | Admin is on the users page with at least one organization node and one role available. | Completing the create-user flow creates the user and opens a one-time key reveal state or modal showing the new runtime key value. |
| AC-016 | User key values remain hidden by default in the console outside the one-time reveal flow. | UI interaction | Admin is on the users page with existing users. | User tables and detail panes do not show persistent plaintext runtime keys by default. |
| AC-017 | The roles page supports create, edit, disable, and assigned-user inspection actions. | UI interaction | Admin is logged in to the console. | The roles page exposes those actions, and each action opens the expected form or list interaction. |
| AC-018 | The API keys page allows managing admin and internal keys but does not allow creating user runtime keys. | UI interaction | Admin is logged in to the console. | The page provides system-key management actions only and contains no create-runtime-key workflow for ordinary users. |
| AC-019 | Policy forms use searchable selectors for user and role subjects instead of raw id text entry. | UI interaction | Admin is creating or editing a resource, field, or masking policy. | Choosing `user` or `role` subject type shows a searchable picker control and no free-text `subject_id` field. |
| AC-020 | The Excel import workflow opens from the users page in a modal that supports click upload and drag-and-drop upload. | UI interaction | Admin is on the users page. | Opening Excel import shows a modal with both a clickable file chooser and a drag target for supported file types. |
| AC-021 | The Excel import modal exposes the organization delimiter configuration with `/` as the default. | UI interaction | Excel import modal is open. | The modal displays a delimiter configuration field prefilled with `/`. |
| AC-022 | Excel import auto-creates missing organization nodes from `org_path`. | API | Valid Excel import payload with a user row referencing a non-existent organization path. | Import preview or execution reports the new organization nodes to be created, and executing the import persists them before or along with users. |
| AC-023 | Excel import places users with empty organization path under the root level. | API | Valid Excel import payload containing a user row with empty `org_path`. | Import execution creates or updates that user with a root-level organization assignment. |
| AC-024 | Excel import uses `external_ref` as the idempotent user identity and updates existing users without rotating their keys. | API | Existing user with external_ref and active runtime key; import payload contains the same external_ref with changed name, org, or roles. | Import updates the existing user record, keeps the existing key valid, and does not mint a new runtime key. |
| AC-025 | Excel import auto-creates missing roles referenced in the `roles` column. | API | Valid Excel import payload references roles not yet present in the database. | Import preview or execution reports those roles as new, and executing the import creates them and assigns them to the imported users. |
| AC-026 | Third-party import connectors normalize imported directory data into the same ingestion pipeline as Excel. | Logic | Import connector fixtures for Feishu, WeCom, or DingTalk are available. | Each connector produces normalized user and organization records that can pass through the shared validation and persistence pipeline without connector-specific branching in the final storage step. |
| AC-027 | Third-party platform imports are manual pull actions only. | UI interaction | Admin opens the importer configuration flow. | The console offers an explicit trigger to fetch from a connector and does not expose automatic schedule or bidirectional sync controls. |
| AC-028 | MCP setup guidance no longer documents caller-supplied identity fields in tool examples. | UI interaction | Admin opens the MCP setup page after the redesign. | The page documents authentication by `X-ADG-API-Key` and tool business parameters only, with no `user_id`, `roles`, or `groups` examples in client snippets. |
| AC-029 | Direct HTTP tool documentation and routes use `/api/tools/{tool_name}` and authenticate through the runtime key alone. | API | Running server with runtime tool route enabled. | Posting to `/api/tools/{tool_name}` with a valid bound runtime key succeeds for supported tools without identity fields, and invalid routes or unsupported methods fail deterministically. |
| AC-030 | The redesigned admin UI follows the established console design constraints rather than introducing a disconnected visual system. | UI interaction | Admin is logged in and navigates between Users, Roles, and existing console pages. | The new pages reuse the existing console shell, responsive layout behavior, density, and control patterns without adding a new standalone visual theme or decorative landing-style layouts. |
